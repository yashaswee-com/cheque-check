# Environment and secrets

Cheque Check has browser-visible build settings, server-only application credentials, Supabase Auth configuration, Edge Function secrets, and operational CLI variables. Their destinations are separate; a value existing in a local example or schema does not prove it is configured in a hosted project ([environment schema](../src/lib/env/schema.ts#L15-L124), [environment examples](../.env.example#L8-L84), [Edge example](../supabase/.env.example#L7-L28)).

## Quick setup

1. Put local Next.js values in a root `.env.local`; the example file is explicitly labeled for local use. For deployed builds, set values in the hosting platform separately for QA and production ([environment example](../.env.example#L1-L5), [deployment environment schema](../src/lib/env/schema.ts#L64-L109)).
2. Configure Supabase Auth values in the Supabase project, and worker/provider values as Supabase Edge Function secrets. Do not copy service-role, provider, or signing secrets into `NEXT_PUBLIC_*` variables ([Auth local config](../supabase/config.toml#L205-L220), [Edge example names](../supabase/.env.example#L7-L28), [server-only schemas](../src/lib/env/schema.ts#L109-L124)).
3. Keep production, QA, preview, and development destinations distinct. The schema rejects local Supabase URLs for deployed labels and rejects a production app environment on a preview deployment ([environment checks](../src/lib/env/schema.ts#L64-L109), [monitoring checks](../src/lib/env/schema.ts#L15-L61)).
4. Rebuild when changing `NEXT_PUBLIC_*` values because the framework embeds public settings in the client build ([Next config](../next.config.ts#L1-L25), [public environment schema](../src/lib/env/schema.ts#L64-L110)).

## Conditional requirements

- Phone OTP UI defaults off; production phone authentication requires the public Turnstile site key in the build ([schema](../src/lib/env/schema.ts#L75-L108)). Supabase Auth also needs its CAPTCHA secret and SMS provider configured in the hosted Auth project ([Auth configuration](../supabase/config.toml#L205-L220), [phone send flow](../src/features/auth/server/phone-auth.ts#L141-L215)).
- Sentry collection defaults off. If enabled, app environment and release are required; an enabled Vercel Sentry build also needs source-map upload credentials ([schema](../src/lib/env/schema.ts#L15-L61), [Next config](../next.config.ts#L6-L25)).
- The push service reads `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, while the public Zod schema shown in this checkout does not declare that key. The code therefore does not establish schema validation for this setting; verify it in each build ([public schema](../src/lib/env/schema.ts#L64-L110), [push service](../src/features/notifications/services/push.service.ts#L13-L57)).

## Deployment state {#deployment-state}

The repository contains local Supabase defaults, including disabled Twilio SMS and disabled database network restrictions; these are not evidence of hosted project settings ([local database config](../supabase/config.toml#L73-L82), [local Auth and SMS config](../supabase/config.toml#L284-L311)). Never infer deployed values, secret rotation state, hosting environment, or active provider configuration from checked-in sample files ([local example](../.env.example#L1-L5), [Edge example](../supabase/.env.example#L1-L6)).

For service topology and deployment verification see [infrastructure and deployment](infrastructure-and-deployment.md); for which settings are sensitive and why see [security and known risks](security-and-known-risks.md#secret-boundaries).
