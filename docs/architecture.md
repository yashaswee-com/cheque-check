# Architecture

Cheque Check uses feature-owned application code, shared platform modules, a Next.js web runtime, and Supabase services. This page is the repository snapshot guide: it describes checked-in code and configuration, not a live deployment. The route and feature boundaries are visible in the App Router page, feature entry points, and the separate server Supabase client ([dashboard route](../src/app/%28dashboard%29/dashboard/page.tsx#L1), [cheque feature entry](../src/features/cheques/index.ts#L1), [server client](../src/lib/supabase/server.ts#L6-L24)).

## Request and data flow

1. Routes and UI use feature entry points, hooks, services, and repositories; database reads are implemented in repositories ([cheque entry point](../src/features/cheques/index.ts#L1), [cheque repository](../src/features/cheques/repositories/cheque.repository.ts#L53-L90)). ESLint also encodes selected import and layering restrictions ([lint configuration](../eslint.config.mjs#L1-L80)).
2. Browser and server Supabase clients use the public project URL/key with session-specific cookie behavior; the separate admin client uses service-role credentials and is server-only ([browser client](../src/lib/supabase/client.ts#L1-L10), [server client](../src/lib/supabase/server.ts#L6-L24), [admin client](../src/lib/supabase/admin.ts#L1-L12)).
3. Authenticated database operations are constrained by PostgreSQL Row Level Security (RLS), ownership checks, and lifecycle rules in migrations; client-side filtering is not the authorization boundary ([lifecycle policies](../supabase/migrations/20261021000000_lifecycle.sql#L36-L76), [owner and business validation](../supabase/migrations/20261021000000_lifecycle.sql#L90-L149)).
4. Provider-backed workflows use server routes or Edge Functions: OCR calls are mediated by the Next.js server, payment benefits are fulfilled by a signed webhook, and notification workers call providers from Supabase Edge Functions ([OCR route](../src/app/api/ocr/cheque/route.ts#L37-L80), [Razorpay webhook](../supabase/functions/razorpay-webhook/handler.ts#L30-L81), [notification dispatcher](../supabase/functions/notifications-dispatcher/index.ts#L14-L50)).
5. Scheduled reminder and export work uses database-backed jobs and scheduled worker invocation; Vault-backed cron credentials are provisioned separately from app environment variables ([notification cron](../supabase/migrations/20261017000000_notification_platform.sql#L153-L191), [export worker schedule](../supabase/migrations/20261031040000_background_exports.sql#L217-L234), [credential provisioning](../supabase/migrations/20261021070000_cron_credentials_provisioning.sql#L1-L52)).

## Design paradigm

The codebase favors feature ownership at the UI/service/repository boundary and shared contracts for rules used across features. Cheque status transitions live in the domain entity, environment/input schemas use Zod, and query-key factories centralize cache identity ([domain rules](../src/domain/cheque.entity.ts#L1-L120), [environment schema](../src/lib/env/schema.ts#L64-L124), [query key registry](../src/lib/query-keys.ts#L1-L80)). Database constraints, RLS, and RPC checks independently validate server-side writes; a TypeScript boundary is not a substitute for database authorization ([lifecycle migration](../supabase/migrations/20261021000000_lifecycle.sql#L188-L252)).

The app uses bounded reads for interactive pages and aggregates for totals. Cheque lists use the server paging RPC; reports fetch full data only for export workflows, with a durable background path for CSV/JSON ([cheque page repository](../src/features/cheques/repositories/cheque.repository.ts#L53-L168), [report summary and preview](../src/features/reports/hooks/use-report-cheques.ts#L9-L54), [export limits](../supabase/migrations/20261031040000_background_exports.sql#L57-L112)).
